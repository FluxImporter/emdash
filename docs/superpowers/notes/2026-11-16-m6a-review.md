### V5: the template routes on D1

Measured on `189529f` with a temporary counter, reverted before the commit:
- **Queries:** the M5a `countD1`, which wraps the D1 binding's `prepare`, put around every route
  handler by the `route()` helper in `routes.ts`. So `withServices` is included, and EmDash's own
  auth and session queries outside the handler are not.
- **Bytes:** a sum, in `src/emdash/storage.ts`'s `kvCollection`, of the UTF-8 JSON length of every
  document `get`, `getVersioned` and `query` returned. That covers plugin storage only; the schema
  and taxonomy reads are not counted, and Task 0 measured them under 1 KB.

Both values came back on each response. The driver was a temporary Vitest file under
`.superpowers/wt/scratch-t9/`, which used the workerd harness (`sites/dev-cf`, fresh local D1 and
R2). `sites/dev-cf/.wrangler` was backed up before the run and restored after it; `git status` was
clean afterwards.

The site, built in this order:
- the M4b links fixture (`createLinkSchema`, byline slugs `cf-v5-alex`, `cf-v5-sam`), whose `posts`
  collection has two reference fields (`author` to people, `related` to posts) and two taxonomies
  (a hierarchical category, a flat tag), with `PEOPLE_CSV` imported first, since `author` matches
  by import key;
- eight saved templates of 256 KiB (`paddedTemplate("cf_v5_big", TEMPLATE_MAX_BYTES)`), created
  first, so that they fill the first list page;
- "v5 other": the posts template reduced to `title`, with `rules.owner: "v5"`;
- "v5 posts": `postsTemplate` with `rules.owner: "v5"`, saved with no problems and one owner
  warning.

**Against the bounds.**
- **Queries.** The worst route is `templates/create` and `templates/import` at 9, under 50 (the
  free plan, spec F6) and under the spec's projection of 10-25. `jobs/create { templateId }` costs
  exactly one query more than the same template inline, as projected.
- **Bytes.** The two full pages are the worst reads: `templates/list` reads 2,099,488 bytes (2 MiB
  + 2,336) and `jobs/list` 2,103,912 (2 MiB + 6,760). Both are within 0.4 % of 2 MiB, so the
  spec's "about 2 MiB" holds, and it is recorded as measured, not loosened (preflight F13).
- **Owner checks.** They read one or two whole rows in this realistic setup. The misconfigured
  worst case (100 rows of 256 KiB with one owner and collection) was not measured; it stays
  projected at about 26 MB (spec Open issues).
- **Inline-template jobs.** A plain `jobs/list` page of such jobs can read up to 8 × 1 MiB (Open
  issues).
- **Production D1** remains unverified (Open issues).

## Open issues

- **Inline-template jobs in `jobs/list`** (final review). A job with an inline template can hold up
  to 1 MiB (the conditional-write cap), so a plain `jobs/list` page of 8 can still read about
  8 MiB. The fix is summary rows or a trimmed response, in M6c (whose `import_status` tool reads
  jobs) or M7 (the admin's job list).
- **The `__proto__` duplicate filter misses Zod's plural message** (final review, cosmetic).
  `shape.ts` drops the singular `Unrecognized key: "__proto__"` at the walk's path but not
  `Unrecognized keys: "x", "__proto__"`, so a strict object with another unknown key reports the
  `__proto__` key twice. Left for any later shape change; nothing depends on it.
- **The fakes.** The Task 1 review deferred two fake-fidelity minors to this note:
  - Minor 2: the `orderBy` cursor is still an offset (plan Ruling 2). EmDash pages `orderBy` by keyset
    too, and throws a `StorageQueryError` on mixed directions with a cursor. The callers that order by
    `seq` page rows that never move, so nothing breaks, but the fake can't catch a skip-on-delete bug on
    those paths.
  - Minor 4: a malformed cursor gives the fake an empty page, where EmDash's `decodeCursor` throws.

  The fake also counts revisions where EmDash uses UUIDs.

  Every result that matters is proven on SQLite and D1 by Tasks 7 and 8.
- **Equivalent mutants left alive.**
  - Task 2: the `!Array.isArray` and `Object.hasOwn` guards, and the unbounded head window, which costs memory only.
  - Task 3: the name check's `self`.
  - Task 5: the first `sameTemplate` guard, since replaced.
- **From the spec's Open issues** (each documented there):
  - the name race (Ruling 5);
  - stale site checks between saves;
  - owner checks only on the template routes;
  - the owner check reads whole rows;
  - plain-text template bodies;
  - `baseUrl` in exports (Ruling 40);
  - unsigned files;
  - one extra run per URL source after the upgrade, and job options not compared by the skip;
  - a dangling `templateId` on the jobs of a deleted template;
  - downgrade rows refused at use.

  A template `version` 2 would upgrade rows in `readSavedTemplate` (spec "Versioning").
- **Production D1 is unverified.** Every V1-V5 result is from local workerd and D1. The first
  deploy should repeat Step 2 against production, and the free plan's 50-query limit (spec F6)
  should be checked there, together with EmDash's own per-request queries (auth, session), which
  the counter does not see.
