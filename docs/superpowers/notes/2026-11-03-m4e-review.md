### Final branch review

One round of fixes (`4d96faa`, and `31aa915` for the Node test's expected message). A re-review
of `4d96faa` approved it.

1. **Important: a template without `translationOf` overwrote the group's shared values.** Such a
   template had no translation checks at all, so a plain French template mapping `price` would
   update a French translation's `price`, and EmDash would sync it to the English source and every
   other locale. Now any template, with or without `translationOf`, fails
   `translation_of_missing` when the entry is a translation (its group is not its own ID) and the
   template maps a shared value (a non-translatable field in the job's snapshot, a reference field
   or a taxonomy). A template that maps only translatable fields still updates a translation. The
   error keeps the field `translationOf` even when the template does not map it (spec, "Templates
   without translationOf").
2. **Important: crash repair saved the link before the decisions, and a record without a value
   could take a translation.** The repaired link was written as soon as the entry was found, so a
   record that then failed (for example `translation_of_missing`) still left a link to an entry
   it was not allowed to write. It is now saved only after the translation decisions pass. In a
   template that maps `translationOf`, a record without a value is an entry of its own and never
   takes an entry that is a translation.
3. **Minor: the `translation_exists` message** claimed the entry was made by someone else ("that
   this import did not create"), which a missed crash repair makes false. It is now "The source
   entry already has a translation in fr (entry <id>), which is not this record's entry".
4. **Minor: silent fallbacks.** The source locale (`?? ""`) and the linked create's value
   (`mapped.translationOf ?? sourceKey`) became typed state: `sourceLocaleOf` throws an internal
   error when a stored job has no source locale, and the record context carries
   `{ sourceId, value }`.

## Rulings

The plan's rulings 1-14 hold as written, with these amendments from the reviews:

- **Ruling 2** (messages): `translation_exists` now reads "… (entry <id>), which is not this
  record's entry". The refusal of a template without `translationOf` has its own message (spec).
- **Ruling 4** (crash repair, guarded) extended: an entry found by the value must also be in the
  source's group (any group when the source is not found); a record without a value in a template
  that maps `translationOf` never takes a translation; the repaired link is saved only after the
  decisions pass.
- **New:** a template without `translationOf` that maps a shared value fails
  `translation_of_missing` (field `translationOf`) on an entry that is a translation. This is
  fail-closed: it fails even when the shared values already match the group, where M4d planned
  `unchanged`.

The spec is brought in line with these in the same commit as this note.

## Open issues for the next part

- **Crash repair's adoption window.** A linked record's crash repair takes an entry found by the
  value when the earlier row is `writing` and the entry is in the source's group. After a crash
  between the `writing` row's save and the linked create, an editor who translates the source in
  the job's locale before the retry has that translation taken as the record's entry and
  overwritten. The window is wider when the source is gone (not found), because the group is then
  not checked. Related: a template **without** `translationOf` that maps only translatable fields
  is repaired by its own key as in M2, so it can be repaired into a translation whose source key
  equals the record's key and overwrite that translation's translatable content.
- **Ambiguous `flux_source_id` in the job's locale.** Crash repair and the reference fallback use
  `findBySourceId` in the job's locale. A translation there carries its source's key (F1), so an
  entry of its own whose key equals that source key (from a record without a value, or another
  template) collides with it. `findBySourceId` then fails `ambiguous_source_id`, and the record
  cannot be repaired until one of the two is trashed or rekeyed.
- **A partial linked create on D1 leaves an orphan.** D1 runs a create's statements without a
  transaction, so a linked create that fails after its insert (the importer sees an error, records
  a failed row and saves no link) leaves the entry in the group. Crash repair does not take it
  (the row is not `writing` and names no entry), so every retry fails `translation_exists` naming
  the importer's own entry, which has to be trashed by hand.
- **A dry run cannot predict two rows naming one source.** Two records of one job that name the
  same source both plan `create` in a dry run (nothing is written, so the group read finds no
  entry for either); the real run creates the first and fails the second `translation_exists`
  (unit test "fails the second of two records that name the same source").
- **V4's outcome.** A source sync moves the translation's `_rev` and gives a pending draft a new
  draft revision. A translation with the importer's pending draft (`publish: false`) then reports
  `pending_draft` on its next run when that run plans an update, and otherwise stays `unchanged`
  and unpublished, also with `publish: true`.
- **i18n turned off.** On a site that had translations and then turned i18n off, the refusal of a
  template without `translationOf` that maps shared values (`translation_of_missing`) is stricter
  than needed, because EmDash no longer syncs shared values without i18n. It fails safe.
- **Jobs created before M4e.** Their field snapshot has no `translatable`, so that refusal sees
  only their references and taxonomies. Such a job, resumed after the upgrade, could still write a
  non-translatable field into a translation. The window is narrow (a job started before the
  upgrade and still running after it).
- **Fail-closed refusal.** A template without `translationOf` whose shared values already match the
  group now fails `translation_of_missing` where it used to plan `unchanged` (documented in the
  spec). The error reuses the code and the field `translationOf` although the template does not
  map it (documented in the spec).
- **Spec-listed issues, unchanged.** Copied byline credits show only where the byline has a row in
  the translation's locale (F5, Fact E1); `translation_not_linked` and the missing-source warning
  repeat on every run; a translation whose source was deleted keeps its group, so its shared values
  are frozen and a record for it without a value fails `translation_of_missing`; the
  `flux_source_id` fallback of a `match: "key"` reference finds a translation by its source's key;
  the M2 cross-job duplicate window becomes `translation_exists` for linked records; a missed crash
  repair ends in `translation_exists` naming the importer's own entry; term translations are not
  linked.
- **No measured D1 query count for linked batches.** A template with `translationOf` uses
  `WORKERS_LINKED_BATCH_CAP` (10 records) and the M4b cost model; the query count per linked batch
  on D1 was not measured. The estimate is about 500 queries per 10 records, inside the Workers
  limit but not confirmed.
- **The parity test does not cover sync or publish on D1.** `parity.test.ts` proves the linked
  create, the shared values, the re-run and `jobs/retry` on D1; the source sync (V4), `publish:
  false` then `true`, and the editor's translation are proven on Node only (and V1-V6 by the
  drafting probe on both).
- **Minor test gaps** (from the re-review of `4d96faa`): the refusal of a template without
  `translationOf` staying quiet when the entry's group is NULL or equal to its ID is not tested;
  there is no dry run of that refusal; and no test where only a reference field causes it (the
  unit test covers a non-translatable field alone and a taxonomy alone).
