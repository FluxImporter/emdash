## Deviations from the plan

- **Task 0 skipped.** V1 and V2 were proven by the plan agent while prototyping (and V1 again on
  workerd by Task 8); see above.
- **Template-mode compatibility (Task 6 ruling, spec updated in 9128ce4).** In template mode an
  existing field of another type that the mapping can fill (for example a `number` mapping and an
  `integer` field) plans `unchanged`, not `conflict`; explicit `fields` still require the exact
  type. The change row reports the requested type (manual check 1: `stock` shows `number` while the
  field stays `integer`).
- **Unmapped unsupported fields (Task 5).** An unmapped field the importer cannot fill and that
  would block every write is a template problem at job creation, a little beyond the spec wording.
- **Named-zone gap times (Task 2 ruling).** With a `z` token in the format, a time in a DST gap
  follows Luxon's behaviour rather than failing with `invalid_date`.
- **Fix rounds beyond the plan's code.** Task 1: JSON `Infinity` and deep nesting refused. Task 2:
  text offsets applied once, date-only values on DST-gap midnights, time-only text, bad zones and
  bare numbers refused, ISO text must start with a year, time tokens told from week-year tokens.
  Task 3: a format Luxon refuses is `invalid_date`, not a job error (pre-existing since M2). Task 4:
  `-0` and `0` compare equal (pre-existing since M2). Task 5: map values match options as the
  converters do, case-duplicate options. Task 6: a partial result on a non-coded error, trimmed
  labels and options, a `FIELD_EXISTS` re-plan that would create again stops, `SchemaError` matched
  by name. Final review (1c363eb): template options matched case-insensitively as the converters
  do, text rules applied to option-less selects, stale `add_options` avoided, unusable map values
  reported as conflicts.
- **Integration expectation (Task 7, 0e2c94e) and workerd (Task 8).** The `stock` assertion was
  changed to `unchanged` after the Task 6 ruling, on both sites.
- **Brief commands.** `pnpm test:cf` was not re-run for this note (Task 8's run at the same commit
  stands). The manual checks needed `dryRun: false` in `jobs/create` (the route requires it) and an
  integer `stock` created first, as noted above.

## Open issues for the next part

- **Known gaps from the plan.** A top-level boolean in a `json` field reads back as `1` or `0`
  (Fact E4); text that EmDash reads back as JSON still plans an update unless it is canonical JSON;
  `schema/apply` cannot create required, unique or defaulted fields or change validation other
  than adding options, and EmDash refuses to make an existing field required (Fact E3); URL-field
  safety stays with EmDash (`emdash_validation_error`); a `json` value of up to 1 MiB is also stored
  in the job's record row as a planned change.
- **Deferred from the task and final reviews:**
  - Template-time check of date formats: a format Luxon refuses is only found per record
    (`invalid_date`), not at job creation (Task 3, final review).
  - A `__proto__` key in a `map` is silently dropped by Zod (Task 3, final review).
  - A blocked field reported as a conflict even when the field would work (final review).
  - Case-duplicate `map` values can add options that differ only in case, which are then ambiguous
    (final review).
  - `unique` fields are not pre-checked; a duplicate stays an EmDash error (final review).
  - `targetFields` is stored on the job without a size cap (final review).
  - `field-types.test.ts` restores the site timezone in `afterAll` to `UTC` when none was set,
    rather than removing the setting (final review).
- **Log CSV.** One `error_code` column per record, and an empty `source_key` for records that fail
  mapping (manual check 4); both pre-date M4a.
- **Known WSL flake.** `crash.test.ts` can fail when the clock steps back during a server restart
  (M3c Fact F1); it did not in this run.
- M4b (taxonomies, references, bylines), M4c (media) and M4d (Portable Text) build on
  `fieldConverter`, the field snapshot and `schema/apply`. The M2-M3d open issues
  (`2026-10-08-m2-review.md` through `2026-10-27-m3d-review.md`) are unchanged by this milestone;
  the production Cloudflare build blocker from M2 still stands.
