## Regular expressions and single-step work

Regex literals are rejected at job creation (user ruling; a backtracking regex ran for 85 s on a 36-character string, J8 in the plan). A safe regex engine may come later. What remains is size-bound single-step work such as `$pad` with a huge width (about 2 s for 100 million characters on Node, J11), ended by V8's length limits.

## Deviations from the plan

- `$shuffle` is also rejected, alongside `$now`, `$millis` and `$random` (ruling in Task 1: it uses `Math.random`, so it breaks determinism). Spec and constraints were updated; Task 1 fix round added the test.
- Banned names are rejected on any reference, not only calls (`$map(a, $random)` would bypass a calls-only check). A lambda parameter named `$now`, `$random` or `$millis` is therefore rejected too (a test pins it); the user renames it.
- "Templates cannot define `$` variables or functions" means template-supplied bindings; `:=` and lambdas inside an expression are allowed (the runaway-expression tests rely on it).
- Task 2 replaced all 17 occurrences of `applyTemplate(` (plan said 16 calls); Task 3's `getJob` edit used surrounding context because `return job;` is not unique. No effect on behaviour.
- The jobs test "does not run expressions" was renamed to say what it asserts (creation succeeds without evaluating against the sample).
- One extra record-level test: a non-step limit (sequence or depth) also yields `expr_limit`.
- `sources/sample` accepts `source.filter` and ignores it (samples show raw records), so a user may expect a filtered sample.
- Unused `CompiledExpression.text` was dropped.
- Test totals run 5 over the plan: unit 27 files / 486 tests.
- The `test:cf` run took 18 m 37 s, a little over the plan's 15 minute estimate; this machine's 10,000-row case is slower.

## Open issues for the next part

- Field names `filter`, `key` and `slug` share the error-field namespace with template fields; they could be reserved in the `fields` refinement.
- `runBatch` compiles the template after `ensureSourceIdField`, so a broken stored template still runs the one-time schema step before the job fails with `invalid_template`.
- The template reader turns a stored mapping with neither `from` nor `expr` (hand-corrupted) into an empty-path lookup.
- No test pins that `invalid_template` is raised before the source is read (a missing `uploadId` with a bad expression).
- The batch release path returns the raw stored job when the lease holder changed; it should return `upgradeJob(stored)` (only matters mid-deploy).
- Integration: the computed title is checked only for SKU-4 (could map all six kept entries); the re-import asserts counters only (no `created: 0`, no stored-entry check).
- workerd: the runaway job does not assert that no entry was created, and two scenarios share one `it()`.
- Manual check 3: the failed record's `sourceKey` is `null` although `key` is a plain `from: "sku"` column; this follows the existing behaviour of failing records (not checked against M3a here), worth confirming.
- Regular expressions stay unsupported until a safe engine is added; expressions stay deterministic (no clock) until a later milestone adds a fixed job timestamp. Expression CPU per record matters most on Workers, where `WORKERS_BATCH_CAP` (20 records per `jobs/next`) still bounds a call.
- Lint prints an info that Biome's configuration could be migrated (`biome migrate`); not related to M3b.
