Every row of every case reached its expected verdict with no `failed` or `conflict`. The
longest-sequence rollback restored the six entries exactly: status, schedule, draft and data, read
the same before the job and after its rollback.

**Rollback cap.** The longest sequence cost about 185 queries per row, below the 300 the reviewer
estimated, so three rows ran 555 and the cap stays 3. The cap comment in
`src/plugin/service.ts` now cites these numbers.

**Workers CPU for the wide template.** Local workerd does not report CPU time, so it was measured
on Node with the engine functions: 11 records of the wide template above (about 750 KB of Portable
Text JSON per record).
- Conversion of the Portable Text took about 300 ms (295-310 ms over three runs).
- The sent and current fingerprints of every mapping took 460-490 ms.
- In one pass over the Portable Text, `stableJson` took 93-104 ms and `canonicalRichText` 66-82
  ms, while SHA-256 took only 8-13 ms.

So a full batch of this template spends roughly 0.8 s of CPU in the engine before EmDash's own work.
That is within the paid plan's default 30 s CPU limit, but not the free plan's 10 ms (see Open
issues). The 3.3-3.7 s wall time per batch on local workerd matches that order. The template's
records are near the Portable Text size limits (`MAX_PORTABLE_TEXT_RECORD_SOURCE_BYTES` 512 KiB),
so this is close to the worst case per record.

## Deviations from the plan

- **More measurement than the brief listed**, as the coordinator notes and reviewer B asked:
  - the longest rollback sequence;
  - the own-draft schedule and publish paths and their rollbacks;
  - six linked scheduled drafts;
  - crash repair adopting a sweep, and the rollback after it;
  - a wide Portable Text template.

  For the sweep adoption, rows were set back to `writing` through `wrangler d1 execute`
  (Ruling 12's way of making states no API offers), and the job was resumed by `jobs/retry`.
- **The counter wrapped the whole `jobs/next` route**, `withServices` included, rather than only
  `nextBatch(…)`, so the counts include the job reads and lease. It also returned the call's wall
  time. The extra queries are part of each invocation's real cost.
- **Workers CPU was measured on Node**, because local workerd reports no CPU time. Only the wall
  time per batch on workerd is recorded.
- **Manual checks.** The REST API stood in for the admin screens (no browser), as in M4d-M5a. The
  swept-translation check ran in the same session, before the restore. The script and its bundle
  were not committed.
- **Order of runs.** `pnpm test:integration` and `pnpm test:cf` ran at the same time, on different
  sites and ports. The probe ran after both, then the manual checks after the counter was
  reverted.
- **One code comment changed**: the rollback cap's comment in `src/plugin/service.ts` cites the
  re-measured V7 numbers, as the coordinator's notes asked. No cap value changed.

## Open issues for the next part

- **Translation sync moves `_rev`.** A source-locale publish that syncs non-translatable fields
  into a translation moves the translation's `_rev`, so a later rollback of a job that wrote the
  translation refuses it (`rollback_changed`). It fails safe, and it is the M5a known gap seen from
  the translation's side. Rolling translation jobs back before any later source import avoids it.
- **CPU on Workers for heavy Portable Text.** A batch of 11 records near the Portable Text limits
  spends about 0.8 s of CPU on Node in conversion and fingerprints, most of it in canonicalising
  and serialising the blocks rather than in hashing. That is well within the paid plan's CPU
  limit. It was not measured on a deployed Worker.
- **Measured headroom.** The largest batch was 790 of the 1,000 queries. A template with more
  links per record than the measured one (three references, two taxonomies, two bylines) could
  still exceed the limit at cap 6. The lookup budget is what bounds that case, and it ended no
  measured batch.
- **From the spec's open issues** (each documented there):
  - an unlisted mapping is still converted, so a bad value in it fails an update;
  - a hook that rewrites a value makes the field read as edited;
  - the admin editor's Portable Text round trip is untested;
  - changes to canonical forms read as edits;
  - pre-M5b link rows cannot see term edits or edges set elsewhere, and treat every mapping as
    edited once the entry has moved;
  - a staged slug in the importer's draft reads as edited after an editor's save;
  - truncated reference selections never lift;
  - terms and edges are not fenced by `_rev` within one record's processing time;
  - `publish: false` keeps an earlier schedule;
  - a past `publishAt` publishes now with the import time;
  - the `_rev` format is EmDash's internal one, and both rules that decode it fail closed if it
    changes;
  - a dry run in `create` mode plans `create` for every duplicate key;
  - the fakes' routable check is opt-in.
- **Known gaps from the plan.** `publishedAt` is never backdated. `publish: false` never takes a
  schedule away. Protection does not cover status changes beyond the M2 pending-state rule. A
  rollback restores but never deletes the revisions it and the job wrote. M5c journals its writes
  in the M5a format and extends the revert sequence after step 7.
- **From the ledger.** Equivalent mutants survive in Tasks 4-7 and the fix wave (listed under Fix
  rounds). Task 7's swept-ownership check does not compare references or bylines.
- **Known flakes.**
  - F1 (the WSL clock step during server restarts) did not recur.
  - F2, the workerd `500 INTERNAL_ERROR` from M4d, did not recur in `test:cf` or the probe. Still
    unexplained.
  - F3: `retention.test.ts` fails in setup while `Cursor.exe` listens on `127.0.0.1:4397`. Seen
    again; the file passed on port 4389. Moving the test's port would remove it.
- **Carried forward from M5a** (`2026-11-03-m5a-review.md`), unchanged except the own-draft
  publish path's missing writing row, which the M5b fix wave settled. That includes:
  - references staged in a draft;
  - the staged slug (F5);
  - media and terms that a rollback keeps;
  - `publishedAt` kept by a rollback;
  - a single revert row that restores hundreds of references;
  - the lookup budget's rate;
  - the M5a spec-listed issues.

  The M4e and earlier open issues (`2026-10-08-m2-review.md` through `2026-11-03-m4e-review.md`)
  are unchanged, and the production Cloudflare build blocker from M2 still stands.
