## Deviations from the plan

- **Task 0 skipped.** The plan agent proved V1-V4 on Node and workerd and measured V5 (see above).
- **Workers cap 5 MiB, not 10 MiB.** V5 crossed the spec's 100 MB threshold, so the plan set the
  5 MiB branch the spec defined. The spec's "Size limit" row still said 10 MiB; it is corrected in
  this commit, together with the multiple-of-3 rounding below.
- **Cherry-picks.** Several commits came from task worktrees (Tasks 3, 5 and 6, and Task 8's
  `a94e975`).
- **Fix rounds beyond the plan's code.**
  - Task 1 (ruling): percent-encoding is normalized in the media map key (upper-case hex,
    unreserved characters decoded). The fragment is stripped before the length check, and the MIME
    type is normalized once.
  - Task 3 (security review): the whole buffer is scanned for markup (the scan used to stop after
    1 KB of whitespace). Other fixes: content-type validation without echoing the header, a copy of
    the URL in `onRequest`, empty bodies refused, AVIF compatible brands, Ogg Theora, and validator
    headers checked inside the `try`.
  - Task 5: a URL used twice in a record or batch is downloaded once (a per-batch cache of what was
    obtained), and `created` stays set once true. The stored `mimeType` is checked after a dedupe.
  - Task 7: a refresh hit used to re-download in every batch and could defer a record forever.
    Refresh now runs at most once per job (`row.jobId`), and a 304 rewrites `jobId` and `fetchedAt`.
    A deferred record's `newTerms` and `newMedia` are carried to its row through `job.deferred` (the
    `newTerms` carry has no test).
- **Final whole-branch review (`5ba0789`).**
  - I1: a cached item, or one kept by a 304, is type-checked against the field, so a PDF can no
    longer reach an image field.
  - I2: a download cut short by the batch deadline is deferred instead of failing the record. The
    batch's first download still fails.
  - M1: failures are cached per batch.
  - M4: an unknown `ftyp` brand gives no type instead of a guess. The MP4 brand allowlist was chosen
    by the implementer.
  - The `FakeMedia` storage key for a filename with no dot is fixed.
  - `mediaMaxBytes` is rounded down to a multiple of 3, because EmDash prechecks the padded base64
    size. This is applied on the service path only. The 50 MiB default in `jobs.ts` and `batch.ts`
    is not rounded; only direct callers and tests reach it.
  - M2 and M3 became documented behaviour in the spec: rewriting drops per-use keys, and a dry run
    lists a repeated URL in each row.
- **Stale integration expectations (`b3a40bf`).** The first Task 10 run on `5ba0789` failed two
  tests on the rounding: `media.test.ts` expected "limit of 100000 bytes" and got 99,999, and
  `parity.test.ts` expected 5,242,880 instead of 5,242,878. The coordinator updated both
  expectations. Ruling: the message keeps quoting the rounded-down limit, because it is the exact
  size that is accepted.
- **Brief expectations for the manual checks.** In check 1, the third row's PDF went into `manual`
  and a PNG into `scan`, so that check 2 could succeed. In check 4, the dry run already refused the
  PDF in `scan`, because its URL was a map hit with a known type (a stronger result than "planned").
- **Brief commands.** `pnpm test` was run as `pnpm exec vitest run` in `packages/flux-import` (the
  same script). The manual checks used the REST API rather than the admin screens.

## Open issues for the next part

- **For M4d (Portable Text images).**
  - Normalize each URL with `normalizeMediaUrl` before calling `resolveMedia`. The map key depends
    on it, and a raw URL would miss rows and download again.
  - Handle `MediaDeferred`: let it end the batch without advancing the cursor, as `processRecord`,
    `importPass` and `retryPass` do for fields. Share the per-batch cache, the Workers budget and
    the media deadline with the field resolution.
- **Workers memory.** The 5 MiB cap bounds bytes, not memory. EmDash's placeholder decode scales
  with pixels (up to width × height × 4 ≤ 32 MiB of pixels, about 3 times that at peak; Facts V5
  and E4), so a small but very large-dimension JPEG or PNG can still approach the 128 MB isolate.
  This affects admin uploads too. The importer cannot lower it, only refuse by size. A pixel-count
  pre-check from the image header would be needed to close it.
- **M5 rollback needs its own record of job-created media.** The map's `jobId` and `created` are
  not authoritative:
  - A crash between upload and map write records `created: false`.
  - A later re-download or refresh rewrites `jobId`.
  - The media item's `authorId` is the `jobs/next` caller, not the job.

  Rollback should keep its own list of the items each job created, or cross-check with media
  `createdAt`.
- **Signed URLs.** A URL with a changing signature or token gets a new map key on every run, so it
  downloads again each time (EmDash dedupes the bytes). The token is also stored in the map row's
  `url`. Ignoring query parameters, or redacting them, needs a per-mapping option.
- **Known gaps from the spec.**
  - A dry run cannot report HTTP errors, DNS answers, sizes, types (except for map hits) or whether
    a download would deduplicate to the media the entry already has.
  - Media is never deleted. An item stored for a record that then fails stays in the library and
    the map.
  - Captions, focal points, `darkVariant`, external providers, relative URLs, credentials or
    custom headers for media URLs, and more than one item per field are out of scope.
  - Downloads are sequential.
  - The Workers Free plan is not supported.
  - When any data field of an existing entry changes, mapped media fields are rewritten from the
    library item, dropping per-use keys an editor added.
- **Deferred from the task reviews.**
  - The "before" text in a change is shown poorly for an external-URL or malformed stored value
    (display only; Task 6).
  - An `allowedMimeTypes` list with a non-string entry is ignored as a whole (reachable only by
    editing the database by hand; Task 2).
  - The unrounded 50 MiB default in `jobs.ts` and `batch.ts` (final review).
  - The `newTerms` carry for a deferred record has no test (Task 7).
- **Known WSL flakes.**
  - `crash.test.ts` can fail when the clock steps back during a server restart (M3c Fact F1). It
    did not in this run.
  - The media deferral test can fail the same way. It keeps 2.5 s of slack and did not flake.
  - New: `url-sources.test.ts` sometimes finds port 4395 "in use" at startup when it runs after
    `media.test.ts` (port 4394). That happened in this run and in two runs on `5ba0789`. A port
    monitor saw 4395 free until the test bound it, and the file passes alone. It looks like a
    startup race on WSL, not a product bug.
- **Log CSV.** It has one `error_code` column per record, so a second media or lookup error code
  appears only in the joined message. This pre-dates M4c.
- The M2-M4b open issues (`2026-10-08-m2-review.md` through `2026-10-27-m4b-review.md`) are
  unchanged by this milestone, and the production Cloudflare build blocker from M2 still stands.
